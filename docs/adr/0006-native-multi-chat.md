# ADR 0006: native multi-chat for the "assistant" role

- Статус решения: принято
- Дата решения: 2026-08-23

## Контекст

После Фазы 6 (удаление персоны «Джони», ADR-неявное — см. коммит истории)
роль «помощник» осталась без единственной захардкоженной персоны, но
по-прежнему ограничена ровно одним чатом на процесс. Продуктовое видение
(Фаза 4) требует, чтобы один и тот же бот мог подключаться к нескольким
чатам одновременно, с жёстким на старте лимитом в 5 чатов.

Три варианта обсуждались (Фаза 3):

- **A. Тиражирование Hermes-профилей** — каждый чат обслуживает отдельный
  Hermes-процесс/профиль.
- **B. Native multi-chat** — один и тот же `bot-agi-bot`/`bot-agi-sync`
  обслуживает несколько чатов одновременно.
- **C. Гибрид** — B для «обычных» ботов, A для изолируемых персон.

Пользователь выбрал **B** по трём причинам: лимит в 5 чатов — небольшой
масштаб, где не окупается изоляция отдельных OS-процессов; storage уже
`chat_id`-partitioned и `TurnCoordinator` уже chat-agnostic внутри себя
(Фаза 3, Факт 1); вариант A требовал бы заново собирать generalized-версию
только что удалённого в Фазе 6 Hermes-моста `parilka_chat` под каждую новую
персону — то есть A платит цену реализации на каждый новый чат, а не один раз.

Роль «человек» (ADR 0005) уже архитектурно живёт нативно внутри
`bot-agi-sync` (эксклюзивная MTProto-сессия), независимо от этого выбора —
её текущий объём (одна персона, один чат) остаётся вне рамок этого решения.

## Решение

### Один граф на чат, не общий пул с membership-фильтром

Разведка (2 параллельных Explore-агента) показала: `TurnCoordinator`
chat-agnostic *внутри себя* (нет поля `chatId`), но именно поэтому его
нельзя шарить между чатами — `routeMessage` разливает входящее сообщение на
все активные turns без фильтра по чату. Общий coordinator на несколько
чатов означал бы реальную утечку fold-данных одного чата в turn другого.

Поэтому multi-chat реализован как **N независимых графов** (`coordinator` +
`readTools` + `agent` + `workers[]`), по одному на чат
(`src/bot-daemon/composition.ts`, `BotDaemonChatComposition`), а не как
единый общий пул с проверкой членства. Это даёт нулевой диф в
`src/bot/worker/{turn-worker,dispatch,worker-config}.ts`: `allowedChatId`
там остаётся скаляром, `claimNextBotTurn` по-прежнему вызывается с одним
`chat_id` на пул. Дешёвые чат-агностичные ресурсы
(`CanonicalBotReadCache`, `BotMemoryTools`, `BotMediaTools`, publisher,
единственный `getUpdates`-поллер) остаются singleton — их конструирование
уже было параметризовано по вызову, не по конструктору.

### Один `BotUpdateProcessor`, но `coordinators: Map<chatId, TurnCoordinator>`

Telegram допускает только одну `getUpdates`-сессию на bot token — поэтому
поллер и процессор остаются едиными на процесс (расширение владения, не
третий процесс, не второй поллер). `BotUpdateProcessor` резолвит нужный
coordinator по `chatId` входящего апдейта перед `routeMessage`
(`src/bot/runtime/update-processor.ts`). `normalizeTelegramUpdate`
(`src/bot/telegram-update.ts`) принимает `allowedChatIds: ReadonlySet<string>`
вместо одного `allowedChatId`; approval-chat bypass (ADR 0005) логически не
меняется, но конфигурация теперь явно проверяет disjointness между
approval-чатом и списком ассистентских чатов
(`assertBotDaemonConfiguration`) — раньше это было неявным допущением.

### Найденный и исправленный баг: per-claim quarantine убивала бы соседние чаты

`claimNextBotTurn` вызывал `quarantineBotTurnsOutsideChatLocked(chatId, ...)`
на каждый claim, что при одном чате самоисцеляло backlog после
реконфигурации allowlist. При нескольких *одновременно валидных* чатах эта
же проверка дед-леттерила бы queued/failed турны любого чата, кроме того,
для которого вызван claim — реальный регресс, не гипотетический. Исправлено:
quarantine вынесен из `claimNextBotTurn` в отдельный публичный
`store.quarantineBotTurnsOutsideAllowlist(allowedChatIds, nowMs)`,
вызываемый один раз при старте демона с полным списком сконфигурированных
чатов (`src/bot-daemon/production.ts`), сохраняя исходный смысл (самоисцеление
после реконфигурации) без кросс-чатового разрушения.

### Конфигурация: JSON-файл вместо одиночных env-переменных

`BOT_CHAT_ID`/`BOT_CHAT_TITLE`/`BOT_PERSONA_PROMPT` как обязательные
одиночные scalar удалены (обратная совместимость с ними не сохраняется —
решение принято ещё в Фазе 5/6 и подтверждено здесь: «чистый лист»).
Вместо них — `BOT_MULTI_CHAT_CONFIG_PATH`, абсолютный путь к JSON-файлу с
массивом из 1–`MAX_ASSISTANT_CHATS` (=5, `src/bot-daemon/multi-chat-config.ts`)
записей `{chatId, chatTitle, personaPromptPath, approximateMemberCount?}`.
Персона каждого чата — отдельный markdown-файл (`personaPromptPath`), не
инлайн-строка в JSON: избегает экранирования многострочного текста и
продолжает уже принятый в Фазе 6 паттерн «персона — читаемый markdown-
документ». Формат переиспользует существующий в репозитории прецедент
(`BOT_MODEL_CONFIG_PATH` → JSON-файл, `src/providers/model-router/config.ts`),
а не изобретает новый.

## Следствия

- `BotRuntimeConfig` (`src/bot/runtime-config/contracts.ts`) больше не несёт
  `allowedChatId`/`chatTitle`/`approximateMemberCount` — эти поля переехали
  в `AssistantChatConfig`, один на чат. `historyDescription` остался в
  общей конфигурации: это не идентичность чата, а общее описание
  доступности памяти, разумно единое для одного бот-аккаунта.
- `ComposeBotDaemonOptions.chats`/`BotDaemonComposition.chats` заменили
  единственные `config.allowedChatId`/`coordinator`/`readTools`/`agent` —
  вызывающий код (`production.ts`) резолвит нужный чат-граф через
  `composition.chats.get(chatId)`.
- `MAX_ASSISTANT_CHATS = 5` — именованная константа, не архитектурное
  ограничение (Фаза 4 явно потребовала конфигурируемости): поднять лимит
  позже — однострочная правка, не редизайн.
- Ни один существующий production-путь роли «человек» (ADR 0005) не
  изменён: approval-чат по-прежнему один, human-persona остаётся
  single-chat в этом объёме.
- Побочная уборка в этом же slice: мёртвые fallback-ссылки на удалённый
  `BOT_CHAT_ID` убраны из `src/digest-cli/options.ts` и
  `src/hermes-projection/cli.ts`/`bin/bot-agi-hermes-project` — они больше
  никогда не срабатывали бы, так как ни один процесс это имя переменной
  больше не выставляет.

## Альтернативы

- **Общий `TurnCoordinator` с membership-проверкой вместо N графов** —
  отклонён: `routeMessage` не имеет понятия чата внутри себя, шаринг
  означал бы утечку fold-данных между чатами. N независимых графов дают
  корректность бесплатно, ценой дублирования дешёвых объектов
  (`BotReadTools`-обёртки, воркеры), не дорогих (кэш, инструменты памяти/медиа
  остаются singleton).
- **Тиражирование Hermes-профилей (A)** — отклонён: требует пересобрать
  generalized-версию удалённого в Фазе 6 `parilka_chat`-моста под каждую
  новую персону, платя стоимость реализации многократно вместо одного раза;
  5 параллельных процессов ощутимо тяжелее одного multi-chat-воркера при
  таком небольшом лимите.
- **Numbered env vars (`BOT_CHAT_1_ID`, `BOT_CHAT_2_ID`, ...) вместо JSON-
  файла** — отклонён: многострочная персона-проза в `.env` уже требовала
  экранирования `\n` даже для одного чата (Фаза 6); JSON+markdown-файлы
  избегают этого полностью и переиспользуют существующий в репозитории
  файловый паттерн конфигурации.
