# ADR 0005: opt-in "human" persona role, split across the two existing processes

- Статус решения: принято
- Дата решения: 2026-08-23

## Контекст

Единственная роль бота сегодня — «помощник»: живёт в `bot-agi-bot`, отвечает
только на адресованные сообщения через Bot API, никогда не скрывает, что
является ботом, и форматирует ответы как Telegram Rich Message. Запрошена
вторая, принципиально другая роль — «человек»: не идентифицирует себя как
бот, инициирует сообщения сама (не только отвечает), и по возможности
имитирует манеру речи конкретного реального участника чата.

Три факта определили форму решения, а не выбор из готового списка вариантов:

1. **Bot API технически не подходит.** Telegram видимо помечает Bot API
   аккаунты как ботов в интерфейсе клиента (суффикс `bot` в username, бейдж
   "BOT"), независимо от качества промпта. Единственный технически пригодный
   транспорт — MTProto-сессия обычного пользовательского аккаунта, то есть та
   же сессия, которой уже владеет `bot-agi-sync` (`src/telegram/exclusive-
   owner.ts`). Пользователь осознанно принял связанный риск (нарушение ToS
   Telegram, риск бана номера) как решение, а не как техническое ограничение
   для смягчения.
2. **MTProto-сессия эксклюзивна и переиспользуется, не дублируется.**
   `assertExclusiveMtprotoOwner()` не допускает второго владельца той же
   сессии. Пользователь решил переиспользовать существующую личную сессию
   (не заводить отдельный номер на персону), поэтому роль «человек» обязана
   жить внутри `bot-agi-sync`, а не в третьем процессе.
3. **Interactive-кнопки — привилегия только Bot API.** Обычный
   MTProto-клиент не может прикрепить `reply_markup` к сообщению. Поэтому
   approval-UI (approve/reject/regenerate/edit) обязан жить в `bot-agi-bot`,
   и Bot API допускает только одну сессию `getUpdates` на токен (конкурентный
   вызов получает `409 Conflict`) — значит `callback_query` обязан идти через
   тот же единственный поллер, что и обычные сообщения, а не через второй.

Из этих трёх фактов следует архитектурная форма: **роль «человек» расширяет
владение двух уже существующих процессов, а не добавляет третий.**

## Решение

### Разделение ответственности

- `bot-agi-sync` (расширено): решает, когда инициировать сообщение
  (`src/human-persona-trigger/`), и отправляет его (`src/human-persona-
  send.ts`) через уже принадлежащий процессу `TelegramGateway`.
- `bot-agi-bot` (расширено): постит approval-запросы с inline-кнопками
  (`src/human-persona-approval-poster.ts`) и обрабатывает решения через
  `callback_query`/reply-правки (`src/bot/runtime/update-processor.ts`).
- Обмен состоянием между процессами идёт только через уже разделяемую versioned
  SQLite (три новые таблицы, см. ниже) — без event bus, без нового IPC,
  согласуется с анти-event-bus контрактом `AGENTS.md`.

### Trigger-engine: двухступенчатая оценка

Эвристический гейт (`src/human-persona-trigger/heuristics.ts`) — чисто
ресурсный: тайм-окно активности, rate-limit, тишина по времени. Никакого
суждения о теме/содержании. Только если гейт пройден — LLM-оценка (роль
model-router `"turn"`, не `"summary"`, так как результат — реальное сообщение
в чат, а не аналитика) с полным контекстом: свежий хвост переписки +
style-profile персоны. Осознанно **не** используется keyword/embedding
pre-filter для содержательной релевантности — приближённые эвристики хуже
прямого суждения модели, а лишний слой не нужен там, где модель уже
справляется (анти-overengineering контракт `AGENTS.md`).

### Style-profile: компилированный документ + верифицированные примеры

Офлайн-pipeline (`bin/bot-agi-human-persona-style`, `src/human-persona-
style/`) читает историю сообщений целевого человека и делает два bounded LLM-
вызова: (а) компилирует описание манеры речи, (б) выбирает до 12 характерных
сообщений **по `messageId`** — реальный текст резолвится на стороне
приложения из уже сохранённых сообщений, а не берётся из ответа модели
напрямую. Регенерируется только когда хеш источника меняется (source-hash
invalidation, механика как у `src/digest/`, без его day/week rollup —
профиль это один артефакт на (персону, цель), не серия по дням). `consent_
basis` — обязательное поле без дефолта на уровне схемы
(`human_persona_style_profile.consent_basis NOT NULL CHECK(...)`): строка не
может существовать без явно записанного основания для анализа истории
целевого человека.

### Approval-workflow: очередь предложений, не прямой вызов

Новая таблица `human_persona_pending_proposal` — очередь с состояниями
`pending → claimed → {approved, rejected, regenerate_requested, edited} →
sent/expired`. Каждый переход гейтится текущим статусом в `WHERE`
(`status = 'claimed'` и т.д.), поэтому повторная доставка одного и того же
Telegram-апдейта естественно идемпотентна — отдельная таблица дедупликации
не понадобилась.

- **Автономность — настраиваемый параметр персоны** (`autonomy_mode`), не
  зашитый выбор: `approval` (по умолчанию, безопасный старт) или `auto`.
  Auto-режим самоодобряется через тот же переход `recordHumanPersonaPropos
  alDecision`, что и approval-режим, — не отдельная машина состояний.
- **"Edit" — не мутация состояния, а UI-хинт.** Клик по кнопке ничего не
  меняет в БД; реальная правка ловится как обычный Telegram-reply на
  запощенное сообщение (`getClaimedHumanPersonaProposalByApprovalMessage`,
  matched по `approval_chat_id` + `approval_message_id` + `reply_to_
  message_id`), пока предложение остаётся `claimed`.
- **"Regenerate" переиспользует LLM-решение trigger-engine**, но осознанно
  пропускает эвристический гейт (человек уже попросил прямо сейчас) и не
  увеличивает rate-limit счётчик (`recordHumanPersonaInitiation` не
  вызывается) — supervised-коррекция не является новой автономной
  инициацией.
- Approval-чат — отдельный Telegram-чат, не чат персоны.
  `normalizeTelegramUpdate` получил explicit bypass
  (`humanPersonaApprovalChatId`) для этого одного чата: сообщения оттуда
  проходят мимо single-chat allowlist, но никогда не попадают в mention-
  detection или `TurnCoordinator.routeMessage` основного ассистента —
  approval-чат структурно не может повлиять на fold/turn state роли
  «помощник».

## Следствия

- Ни один существующий production-путь роли «помощник» не изменён:
  `send-handlers.ts`'s approval-token MCP-gate, Bot API single-chat
  allowlist для обычных сообщений, `TurnCoordinator` — всё осталось как
  было; роль «человек» добавляет параллельные ветки, а не переписывает
  существующие.
- Оба процесса остаются per `AGENTS.md` "два явных долгоживущих процесса" —
  расширение владения задокументировано явно (см. правку контракта), а не
  тихо.
- Вся новая функциональность **выключена по умолчанию**: без
  `BOT_HUMAN_PERSONA_ID`/`BOT_HUMAN_PERSONA_CHAT_ID`/`BOT_HUMAN_PERSONA_
  TARGET_USER` (и, отдельно, `BOT_HUMAN_PERSONA_APPROVAL_CHAT_ID` для
  approval-поста) trigger/send/poster-runner просто не конструируются —
  поведение обоих процессов не меняется.
- ToS-риск MTProto-аккаунта и этический вопрос согласия на "оцифровку"
  реального человека остаются операторскими решениями вне кода — система
  их не проверяет и не может проверить, только фиксирует явно заданное
  `consent_basis` как evidence принятого решения.

## Альтернативы

- **Третий процесс под роль «человек»** — отклонён: либо конфликтует за ту
  же эксклюзивную MTProto-сессию, либо требует отдельного номера
  (пользователь явно решил переиспользовать существующую сессию).
- **Bot API для роли «человек»** — отклонён технически, не как компромисс:
  платформа сама раскрывает бота в интерфейсе клиента.
- **Отдельный поллер под `callback_query`** — отклонён: Telegram допускает
  одну `getUpdates`-сессию на bot token, конкурентный вызов получает `409`.
- **Отдельная durable-таблица дедупликации callback-апдейтов** — отклонена:
  переходы очереди предложений уже идемпотентны через status-guarded
  `UPDATE ... WHERE status = ...`, дополнительный слой был бы избыточен.
- **Keyword/embedding pre-filter для триггера и биография-стиль через
  классические NLP-метрики** — отклонены: грубое приближение там, где
  прямое LLM-суждение и так доступно и качественнее.

## Addendum (2026-08-23)

Runtime-конфигурация роли (`BOT_HUMAN_PERSONA_ID/CHAT_ID/CHAT_TITLE/
TARGET_USER/AUTONOMY_MODE/ACTIVE_HOUR_*/MIN_SILENCE_MS/
MAX_INITIATIONS_PER_WINDOW/WINDOW_MS` и отдельно
`BOT_HUMAN_PERSONA_APPROVAL_CHAT_ID`), описанная выше как россыпь
env-скаляров, заменена на единственную опциональную запись `role:
"human-persona"` в общем файле `BOT_BOTS_CONFIG_PATH` — см. ADR 0007.
Решение процессов/владения/workflow из этого документа не меняется, только
формат чтения runtime-конфигурации. `BOT_HUMAN_PERSONA_ID/CHAT_ID/
TARGET_USER/CONSENT_BASIS` для офлайн style-profile CLI (`bin/bot-agi-
human-persona-style`) не затронуты — другой жизненный цикл, см. ADR 0007
«Следствия».
